Your agent keeps the lab notebook while you think

Ganymede Journal lets Claude Code and other agents work through an analysis inside a live TypeScript notebook you can watch, edit and re-run, instead of writing one up at the end.

Spring 2027. Ganymede is a Jupyter server built to be small: one binary that speaks the standard Jupyter API, runs any kernel, and embeds in an app as readily as it runs on a laptop. Today it adds Journal: a drop-in kit that turns any MCP-capable coding agent into a notebook-native research partner. Install one plugin, start a conversation about your data, and the agent records each step as it goes: the question it is asking, the code it ran on the notebook's kernel, the output it saw, and what it concluded. You can follow along in Ganymede's app or JupyterLab, add a cell of your own, or correct the agent mid-stream. When the session ends, the notebook already exists, it has run top to bottom on one kernel, and it reads like a lab notebook.

Until now, agent-led analysis has left two kinds of record, neither of them good. The chat transcript has everything but is unreadable a week later. The notebook the agent writes when asked "turn this into a notebook" is readable but reconstructed: code tidied after the fact, outputs re-run or never run, dead ends gone. Data people have been doing the second step by hand for years, and agents inherited the habit.

Journal changes the order of operations. The agent never runs analysis code anywhere but the notebook's kernel, so the journal is reproducible by construction. Steps that had to happen elsewhere, such as a gh or curl call that needs your credentials, are written in as clearly marked recorded cells and never pass as kernel output. Quick checks the agent makes to orient itself run on the same kernel without cluttering the page. When understanding changes, the agent revises the earlier finding in place, and the notebook keeps what it used to say.

"I kept asking Claude to write the notebook at the end, and I realized I was asking it to redo the work I used to do in Jupyter directly. Now it does the work there in the first place, and I get to sit next to it."Thomas Lockney, Ganymede maintainer (draft quote)

Journal is built from parts that already exist. Ganymede serves the standard Jupyter API, so nb-cli, JupyterLab and VS Code connect unchanged. Its new ganymede mcp command gives agents a handful of tools shaped around one move, "add a cell and run it". The plugin bundles that MCP server with a journaling skill, a few hooks that keep the record honest, and a reviewer agent that reads the finished notebook cold. Nothing in it needs a custom agent harness: it is configuration for the agent you already use.

TypeScript is the default language, through cdp-kernel, with charts from Observable Plot or Vega-Lite and tables from Polars. Any installed kernel works, Python's included. With images turned on, charts come back to the agent as pictures, so it reads the plot it just drew instead of guessing from the numbers.

"The best part is the end. I don't ask for a write-up any more. I read the journal, fix one sentence, and link it in the incident ticket."A platform engineer, fictional early user

To start: install Ganymede and cdp-kernel, then in Claude Code run /plugin marketplace add tlockney/ganymede and /plugin install ganymede-journal@ganymede. Type /ganymede-journal:journal and a question.

Most of it has shipped

This page started on 31 October as a design, with the release above as fiction. Within a week most of it was built. Ganymede 0.5.0 (3 November) shipped document rooms, the execute endpoint and ganymede mcp. Ganymede 0.6.0 (6 November) shipped the ganymede-journal plugin, charts sent to the agent as PNG, "what changed since my last read", and revision history in cell metadata. Tracking issue #239 is closed; the follow-ups are on #311.

What's left is mostly the look: ganymede-ui still edits through the contents API, so the live view today is JupyterLab with the collaboration extension, and the journal view below is a design. Each capability carries one of three statuses; the reality check lists them with sources. The agent side still uses only Claude Code's documented skills, MCP, hooks, subagents and plugins.

Tenets

What the workflow promises

Journal by executing

Analysis code runs only on the notebook's kernel. The notebook is the work, not a write-up of it.

Never pass off a recorded step

Anything that ran outside the kernel is a recorded cell, tagged and styled as such.

Revise, don't append

A wrong finding is edited where it stands, with its old text kept in metadata, so the notebook reads in order.

The human is in the same document

You can watch, add a cell, or change one. The agent notices and works from what is there now.

Ends reproducible

A session ends with restart and run all. If it doesn't reproduce, the agent says so before it says it is done.

Configuration, not a harness

Plugin, skill, MCP server and hooks for an agent you already run. Swap the agent, keep the notebook.

The drop-in kit

What you install, and what each piece does

One Claude Code plugin carries the whole mode. It lives in the Ganymede repo at plugins/ganymede-journal, next to the server it drives, and the repo is its marketplace. The skill follows the Agent Skills format and the MCP server is plain MCP, so those two also work in other agents; the hooks are Claude Code's. Agents over MCP is the reference.

FAQ

Questions a user would ask, and questions we should

External

Why a notebook and not a Markdown report?

A report is written after the fact. A notebook can be re-run: the code, its outputs and the narration live in one file that ganymede execute checks. It also opens in tools you already have.

Can't Claude Code already edit notebooks?

Its NotebookEdit tool edits cells in the file, but runs nothing. Journaling needs a kernel whose state lasts across calls, outputs written back, and a document a person can watch. That's the server's job.

Do I need Python?

No. Ganymede, nb-cli and cdp-kernel are Rust and TypeScript, and the plugin's hooks run on Node. A Python kernel works if you install one.

Does it work with agents other than Claude Code?

The MCP server and the skill do: ganymede mcp is documented for Codex and Cursor too, and the skill uses the Agent Skills format. The hooks are Claude Code's, so another agent gets the conventions without the enforcement.

What does the agent actually see of my outputs?

Text first, in nb-cli's @@cell/@@output format, cut at 4,000 characters with the rest in a file it can open. Tracebacks come back short and without colour codes. Images, SVG charts included, come back as PNG only when the server runs with images on.

What happens to dead ends?

Probes leave nothing. A hypothesis that was tested and failed stays, because the test is evidence; the finding is revised to say so, and the old wording is kept in the cell's history (the last 10 versions).

Can I watch live?

In JupyterLab with the collaboration extension, yes, when the agent uses a shared ganymede serve --mcp. ganymede-ui shows the agent's work after a reload until it moves to rooms (ganymede-ui#183).

Internal

What's left before the release above is true?

The look and the live view in Ganymede's own app: ganymede-ui on rooms (#183), then the journal view and export (#184). Everything the agent does in the session already works with 0.6.0.

Images or a live view: why choose?

Images are a per-server setting. The plugin's default ganymede mcp joins a shared server, which sends images only if it was started with mcp_images = true; --images makes the agent start a private server nobody can watch. Turning images on in the shared server's config gives both, but it isn't the default. Worth deciding whether it should be.

How do we know it works?

evals/journal on main runs three seeded tasks with known answers and a trap each (duplicated rows, a shell step, a unit mix-up) through claude -p with the plugin, then scores the finished notebook: clean run-all, recorded steps passed off as kernel output, findings revised versus appended, and summary rewrites. The baseline hasn't been run yet (#316).

Which open questions got answered?

Recorded cells are Markdown with fenced blocks. The Bash hook records only commands ending in # journal by default. The plugin lives in the Ganymede repo. Scratch runs still leave no trace.

What stays open?

Whether images should be on by default. Whether scratch runs should leave a count. How a journal entry links to the chat that produced it. Whether to move the tested nb-cli to 0.0.11.
